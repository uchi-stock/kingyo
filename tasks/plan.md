# 実装計画: issue #72 AT対応（ポイ中央固定＋金魚側パン方式）

## 概要

現状、ポイ自体が加速度センサーの直接レート制御＋弱い再センタリングでpond相対%位置を移動する（`motion/poiMotion.ts`, `motion/usePoiMotion.ts`）。これをアクセシビリティ対応のため、ポイは常に画面中央に固定表示し、スマホを動かすと金魚側（周囲）がその逆方向に動く（カメラをパンする操作感）方式へ変更する。

## アーキテクチャ決定

- **オフセットの表現**: `poiMotion.ts`の`stepPoiMotion`（直接レート制御＋弱い再センタリング）はロジックを一切変更しない。出力の`xPercent/yPercent`（0-100、中心50）を、従来の「pond相対%位置」ではなく「中心50を基準としたvw/vh単位のワールドパンオフセット」として再解釈する（`offsetVw = xPercent - 50`）。金魚の座標系（`goldfishSwim.ts`）が既にvw/vh基準のため、単位変換なしでそのまま使える。
- **センサーモードのみ対象**: 本Issueの完了条件は「スマホの動きに応じて金魚（周囲）の画面上位置が移動する」（センサー操作時）のみを対象とする。フォールバック操作（`showManualControl`、issue #124のタップ/ドラッグ操作）は、AT対応の主眼（物理的な端末操作を要するセンサー操作の代替）と無関係であり、既存の「ポインタで直接ポイを狙った位置へ動かす」体験の方がポインタ操作としてはむしろ自然なため、**変更しない**。フォールバック時はワールドオフセットは常に中立値（50, 50 = オフセットなし）を保つ。
- **PoiとGoldfishSchoolでのオフセット共有（再レンダー増加を避ける）**: `App.tsx`で`useRef`によりオフセット用のrefを1つ生成し、`Poi`と`GoldfishSchool`の双方へpropsとして渡す（refはオブジェクト参照が安定するため、渡すこと自体は再レンダーを増やさない）。`usePoiMotion`は毎フレームこのrefへ書き込む（センサーモード時は実際の値、フォールバックモード時は常に中立値）。`GoldfishSchool`は既にuseGoldfishSchool独自の60fps rAFループで毎フレーム再レンダーされているため、このrefを描画時に読み取ってtransformへ反映してもレンダーコストは増えない（issue本文が示唆する「refベースで直接DOM書き込み」の方針と整合）。
- **捕獲・逃走判定の位置計算**: `catchGoldfish.ts`・`fleeGoldfish.ts`自体は変更しない（金魚の生座標とポイの「実効位置」を比較する既存ロジックのまま）。センサーモード時、ポイの実効ビューポート位置は「pond要素の中心（リサイズ時のみ変化する定数）＋ワールドオフセット」として計算する。フォールバックモード時は、オフセットが常に中立のため、実質的に現状と同じ計算（pond中心＋自分の位置オフセット）になる。

## リスクと対策

| リスク | 影響度 | 対策 |
|---|---|---|
| Poi/GoldfishSchoolの再レンダー最適化が崩れ、実機でカクつく | 中 | refベース共有を徹底し、オフセットのためにReact stateを新設しない。GoldfishSchoolは既存の60fps再レンダーに乗せるのみとする |
| フォールバック操作（issue #124）の回帰 | 高 | フォールバックモードのロジック・テストは意図的に変更しない設計とする |
| 捕獲・逃走判定の位置ズレ（オフセット計算のミス） | 高 | catchGoldfish.ts/fleeGoldfish.ts自体は不変とし、呼び出し側の位置計算のみをテストで検証する |
| pond要素が画面全体を占めない場合のvw/vh変換の誤差 | 低 | 既存実装と同じ`getBoundingClientRect()`＋`window.innerWidth/innerHeight`変換を踏襲し、新規のズレを生まない |
